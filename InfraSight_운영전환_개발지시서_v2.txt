0-2. DB 테이블 구조 (실측 - init_db() 함수 기준)
--------------------------------------------------------------------
devices (
  id TEXT PRIMARY KEY,        -- uuid4 hex 10자리, 로컬PC는 'local-pc' 고정
  category TEXT,               -- server | db | net | fac
  name TEXT,
  mode TEXT,                   -- local | agent | ping | snmp
  ip TEXT,
  token TEXT,                  -- agent 모드에서만 사용, uuid4 hex 16자리
  fields TEXT,                 -- JSON 직렬화 문자열 (os/role/engine/community 등)
  created_at INTEGER           -- epoch ms
)

incidents (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER,
  severity TEXT,               -- info | warn | crit
  source TEXT,                 -- 장비 이름 (device_id 아님! 이름 문자열)
  category TEXT,               -- SMS | DBMS | NMS | FMS (라벨, device.category와 다른 표기)
  message TEXT,
  status TEXT                  -- open | ack | resolved  (지시서의 OPEN/ACK/RESOLVED와 대응)
)

>>> 분석 결론:
  - 지시서 10번이 요구하는 first_occurred_at / last_occurred_at /
    occurrence_count / acknowledged_by / acknowledged_at 컬럼은 전부
    없음 → 이벤트가 반복 발생할 때마다 새 row가 생성되는 구조
    (중복 폭주 가능성 있음, Phase 2에서 반드시 개선 대상)
  - incidents.source가 device_id 외래키가 아니라 "이름 문자열"이라서
    장비 이름이 바뀌거나 삭제되면 과거 이벤트와 연결이 끊어짐
    → device_id 컬럼 추가 필요 (기존 source는 표시용으로 유지)
  - devices.fields가 통째로 JSON 문자열이라 SNMP community/token이
    사실상 평문으로 같은 테이블에 저장됨 (지시서 20번 항목의 근거)
  - polling_interval, timeout, retry_count, monitoring_enabled,
    vendor/profile, maintenance_* 컬럼 전부 없음 (지시서 4/14/15/18번
    항목 그대로 필요)

0-3. 현재 polling 구조 (실측 - monitor_loop 함수, server.py:490)
--------------------------------------------------------------------
  - 단일 while True 루프 + time.sleep(TICK_SECONDS=2.0)
  - 매 tick마다 SQLite에서 device 전체를 다시 SELECT (load_devices)
  - 장비를 순서대로(sequential) 하나씩 순회하며 mode별 분기 처리
  - 장비별 timeout/interval 설정 없음 - 전부 TICK_SECONDS=2.0 하드코딩
  - SNMP timeout=1.5초 하드코딩 (device 단위 override 불가)
  - Ping timeout=1.0초 하드코딩, retry 없음(1회 실패=즉시 실패)
  - 이미 개선되어 있는 부분: 실제 네트워크 I/O(ping/snmp)는 LOCK
    없이 수행하도록 되어 있어서(주석 참고, server.py:490-494), 웹
    요청이 polling 때문에 막히는 문제는 "부분적으로" 이미 해결됨.
    다만 이것은 "Lock 경합 완화"였을 뿐, 지시서가 요구하는 "Web과
    Collector의 완전한 프로세스/계층 분리"는 아직 아님 (같은 프로세스,
    같은 스레드가 순차 polling 수행 중).
  - 병렬처리 없음: 장비 20대 중 1대가 SNMP timeout(1.5초)이면 그 다음
    장비들은 그만큼 순서가 밀림 (개별 장비 지연이 전체 주기를 늦춤)

>>> 분석 결론: 지시서 3/5/6번이 지적한 문제가 실제로 존재함.
    다만 완전히 처음부터 만드는 것은 아니고, 이미 존재하는
    sample_ping / sample_snmp / sample_agent / sample_local
    4개 함수는 그대로 "Collector의 각 모듈"로 이관 가능한 형태로
    이미 분리되어 있음 (이름만 봐도 역할이 명확함) → 이 부분은 기존
    코드를 최대한 재사용하면 됨. 바꿔야 하는 것은 "누가, 언제, 어떤
    스레드에서 이 함수들을 호출하느냐"는 스케줄링 계층이다.

    /api/agent/report payload에 없음 (추가 필요)

0-5. SNMP 조회 구조 (실측)
--------------------------------------------------------------------
  - pysnmp 7.x, hlapi.v3arch.asyncio 모듈만 사용 (v1arch/구형 hlapi
    사용 안 함) - **완전 비동기 API**
  - 이미 확인된 사실(직접 코드 실행으로 검증함): 이 버전의 pysnmp는
    SNMPv1/v2c는 CommunityData로 정상 동작하나, v3는 UsmUserData
    클래스가 동일 모듈(hlapi.v3arch.asyncio)에 존재함이 확인됨
    (import 가능 여부까지 실제 확인됨). 즉 지시서 19번의 SNMPv3
    "준비"는 존재하지 않는 API를 추측할 필요 없이, 이미 확인된
    UsmUserData로 바로 구현 가능.
  - 장비 1대당 SnmpEngine()을 매 polling마다 새로 생성 (세션 재사용
    안 함). 이미 "장비당 세션 1개로 통합"까지는 개선되어 있음
    (예전엔 OID 그룹마다 별도 engine을 만들어서 훨씬 느렸음).
  - Cisco 전용 OID(CPU/메모리)에 대한 폴백 로직 이미 존재
    (OID_CISCO_CPU_5MIN, OID_CISCO_MEM_USED/FREE)
    → 이것이 사실상 지시서 18번이 말하는 "Vendor Profile"의 초기
      형태임. 완전히 새로 만들 필요 없이, if/elif 체인을
      profile 딕셔너리 구조로 승격시키면 됨.

0-9. 현재 보안 상태 (실측 - 있는 그대로)
--------------------------------------------------------------------
  - app.run(debug=False) 이미 적용됨 (양호)
  - 로그인/세션/권한 개념 전혀 없음 - 누구나 브라우저로 접속하면

  - SNMP community, agent token이 GET /api/state 응답에서는 이미
    제외 처리되어 있음(serialize_device 함수에서 community/snmpPort/
    snmpVersion 필터링, server.py:518) → 이 부분은 이미 잘 되어있음.
    다만 DB 원본(infrasight.db)에는 평문 그대로 저장되어 있고,
    /api/devices POST 요청 자체에는 인증이 없어 누구나 등록 가능.
  - 입력 검증: IP 형식 검사, port 범위 검사 전무 (있는 그대로 저장)
  - SQL: 전부 파라미터 바인딩(?) 사용 중 → SQL Injection 위험은
    현재 낮음 (이 부분은 이미 안전하게 작성되어 있음, 유지만 하면 됨)
  - XSS: 프론트엔드에 escapeHtml() 함수가 이미 존재하고 장비명/설명
    등 사용자 입력을 렌더링할 때 사용 중 → 기본적인 방어는 이미 있음,
    다만 전수 적용 여부는 Phase 3 진행 시 재검증 필요

■ 보완이 필요했던 부분 (이번 버전에서 구체화함)
  1. "적절한 password hashing", "설정 가능하게 한다" 같은 표현이
     반복되는데, 실제로 무엇을 쓸지 못 박지 않으면 구현 단계에서
     매번 판단이 갈린다 → Part 2에서 라이브러리를 구체적으로 지정함.
  2. SNMPv3를 "존재하지 않는 API를 추측하지 말라"고 정확히 경고했는데,
     정작 이 프로젝트의 pysnmp 버전이 v3를 어떻게 지원하는지는
     검증되지 않은 상태였다 → 실제로 import 테스트를 해서 확인함
     (Part 0-5 참고).
  3. Collector 분리(3번), 병렬 polling(5번), 장비 상태 세분화(7번)가
     서로 강하게 얽혀 있는데 순서가 명확하지 않았다 → Part 2의
     Phase 1을 이 세 가지의 통합 작업으로 재정의함.
  4. 프로덕션 배포 방식(28번)이 "Windows Service로 준비" 정도로만
     언급되어 있었는데, 그 전에 Flask 개발 서버 자체를 교체하지
     않으면 Windows Service로 감싸봤자 의미가 없다 → WSGI 서버
     교체를 별도 항목으로 명시함.
  5. 39번 Phase 순서에 "Phase 0: 분석"이 빠져 있었다 (본문에서는
     요구했지만 Phase 목록엔 없었음) → Part 2에서 Phase 0으로 명시.

■ 원본 그대로 유지한 부분
  - 41개 섹션의 번호와 요구사항 자체는 전부 타당하므로 순서/번호를

                   미지원이라 배제. "pip install waitress"만 하면 됨)
  비밀번호 해싱   : werkzeug.security (Flask에 이미 포함, 신규 설치 불필요)
  로그인 세션     : Flask 내장 session + itsdangerous 서명 쿠키
                   (신규 설치 불필요, Flask-Login은 선택사항으로 보류)
  로깅           : 표준 logging + RotatingFileHandler (신규 설치 불필요)
  이메일 알림     : smtplib (표준 라이브러리, 신규 설치 불필요) - 단,
                   실제 SMTP 서버/계정 정보는 사용자가 제공해야 함
  Windows Service : NSSM (Non-Sucking Service Manager, 무료 툴) 권장.
                   pywin32 방식은 코드량이 많아 2순위로 보류.
  설정 저장       : 새 SQLite 테이블 settings (파일 기반 config.yaml
                   대신 - 이미 SQLite를 쓰고 있고, 관리자가 화면에서
                   바로 수정 가능해야 하므로 DB가 더 적합. 단, PORT/
                   SECRET_KEY/DB_PATH처럼 "실행 전에 정해지는" 값은
                   .env 파일 + python-dotenv로 분리)

4/5/6항 (Scheduler / 병렬 / Timeout) - 구체화
--------------------------------------------------------------------
  APScheduler BackgroundScheduler(executors={'default':
  ThreadPoolExecutor(MAX_WORKERS)}) 사용.
  장비 등록/수정 시 add_job(func, 'interval', seconds=device.polling_interval,
  id=f"poll_{device_id}")로 개별 등록, 삭제 시 remove_job.
  이렇게 하면:
    - 장비별 다른 주기가 "설정 가능"이 아니라 "기본 기능"으로 해결됨
    - 한 장비의 timeout이 다른 장비 polling을 절대 지연시키지 않음
      (스레드풀이 알아서 분산)
    - MAX_WORKERS=10 같은 값은 settings 테이블에서 관리

  devices 테이블에 추가할 컬럼:
    polling_interval INTEGER DEFAULT NULL  (NULL이면 종류별 기본값 사용)
    timeout_sec REAL DEFAULT NULL
    retry_count INTEGER DEFAULT NULL
    monitoring_enabled INTEGER DEFAULT 1


7/8항 (5단계 상태 / 장애 종류 구분) - 구체화
--------------------------------------------------------------------
  devices에 컬럼 추가:
    consecutive_failures INTEGER DEFAULT 0
    last_failure_reason TEXT  (PING_TIMEOUT | SNMP_TIMEOUT |
                                SNMP_AUTH_ERROR | AGENT_OFFLINE |
                                COLLECTOR_ERROR 중 하나)
    last_success_at INTEGER
  상태 계산 공통 함수 하나로 통합 (현재 3곳에 복붙된 rank 로직 제거):
    def evaluate_status(consecutive_failures, warn_at=1, down_at=2):
        ...
  COLLECTOR_ERROR는 별도 취급: Collector 자체가 죽은 경우
  (health.py가 감지) 장비 상태를 UP으로 유지하지 않고 UNKNOWN으로
  강제 전환 (지시서 8번 후반부 요구사항, 9번과 직결됨).


9항 (자체 상태 모니터링) - 구체화

    - scheduler.py가 각 collector 함수 실행 성공/실패 시각을 기록
    - Web/API: Flask 자체가 응답하고 있으면 UP (별도 체크 불필요)
    - Database: SELECT 1 실행 성공 여부
    - Collector 전체: 마지막 polling 완료 시각이

    - 신규 API: GET /api/system/health


10/11항 (이벤트 강화) - 구체화
--------------------------------------------------------------------
  incidents 테이블 재설계 (기존 테이블 이름 유지, 컬럼만 추가/마이그레이션):
    ALTER TABLE incidents ADD COLUMN device_id TEXT;
    ALTER TABLE incidents ADD COLUMN event_type TEXT;
    ALTER TABLE incidents ADD COLUMN first_occurred_at INTEGER;
    ALTER TABLE incidents ADD COLUMN last_occurred_at INTEGER;
    ALTER TABLE incidents ADD COLUMN resolved_at INTEGER;
    ALTER TABLE incidents ADD COLUMN acknowledged_by TEXT;
    ALTER TABLE incidents ADD COLUMN acknowledged_at INTEGER;
    ALTER TABLE incidents ADD COLUMN occurrence_count INTEGER DEFAULT 1;
  add_incident()를 upsert 방식으로 변경: 같은 device_id + event_type의
  OPEN 이벤트가 이미 있으면 occurrence_count++ / last_occurred_at 갱신,
  없으면 새로 생성. (기존 ts/severity/source/category/message/status

12/13/14항 (Threshold / Interface 강화 / Interface ON-OFF) - 구체화
--------------------------------------------------------------------
  settings 테이블 (신규):
    key TEXT PRIMARY KEY, value TEXT, scope TEXT (global|device),
    device_id TEXT NULL
  기본 제공 key: cpu_warn, cpu_crit, mem_warn, mem_crit, disk_warn,
  disk_crit (전부 % 정수). device_id가 있으면 해당 장비 우선 적용,
  없으면 global 값 사용 (지시서 12번 "장비별 또는 시스템 기본값" 요구
  그대로).
  interfaces 정보는 현재 entity 메모리 구조체 안에만 있고 DB에
  영속화되지 않음 → interface_settings 테이블 신규 추가:
    device_id TEXT, if_index TEXT, monitoring_enabled INTEGER DEFAULT 1
  snmp_collector.py가 이 테이블을 참조해서 monitoring_enabled=0인
  인터페이스는 DOWN이어도 이벤트 생성하지 않음.

21항 (로그인/권한) - 구체화 + 확인 필요 사항
--------------------------------------------------------------------

  VIEWER), created_at

  로 저장, check_password_hash로 검증.
  @app.before_request 또는 route decorator(@login_required,
  @role_required('ADMIN'))로 API별 권한 체크.
  ⚠ 확인 필요: 이 시스템은 지금까지 "혼자 쓰는 개인/소규모 사무실

  "그냥 브라우저 열면 바로 보이는" 편의성이 사라진다. 정말 여러 명이
  다른 권한으로 접속해야 하는 환경인지, 아니면 "그냥 비밀번호 하나로
  외부인 접근만 막으면 되는" 수준인지에 따라 Phase 3의 범위가
  크게 달라진다. → Phase 3 착수 전 확답 요청.

지적한 문제들(하드코딩된 timeout, 순차 polling, 2단계 상태, 이벤트
중복 생성 가능성, credential 평문 저장, 인증 없는 API)이 그대로
존재함을 확인했다. 이번 v2 문서는 그 위에 "무엇으로, 어떤 순서로"
해결할지를 구체적인 라이브러리·테이블·파일 단위까지 못박았다.

다음 메시지에서 "Phase 1 진행해줘"라고 답하면, 위 Part 2의 Phase 1
내용부터 실제 코드 작업을 시작한다. 기존 기능(장비 등록/Agent/Ping/
SNMP/CPU-Memory/Interface/Traffic/Uptime/토폴로지/기존 DB 데이터)은
Part 0-10에 정리한 대로 하나도 깨뜨리지 않는 것을 최우선으로 한다.
